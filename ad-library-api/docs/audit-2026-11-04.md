# AdSignal audit — 2026-11-04

## Outcome

Scans had been collecting about **one page per query since ~2026-07-15**. Fixed, deployed to the Mac mini
(launchd `com.eladsaar.meta-ad-library-api`, 127.0.0.1:4100) and verified live.

| Measure | Before | After |
|---|---|---|

## Root cause (Meta error 1357054)

Meta rejects the GraphQL pagination POST unless it carries `sec-fetch-site: same-origin`,
`sec-fetch-mode: cors`, `sec-fetch-dest: empty`. Ruled out by A/B test: cookies, referer shape,
`sec-ch-ua`, the frontend `v` revision, `first`, extra comet params. The client reported it as "empty payload"
because Meta signals it via a top-level numeric `error`, not a GraphQL `errors` array. The old watchdog fetched
page 1 only, so it stayed green. Timeline from the DB: avg unique ads per scan 213–664 (Jul 12–14) → ~90 from Jul 15.

## Other defects fixed

- Quoted phrases silently ran as unordered keyword searches (`keyword_exact_phrase` never used: 1,286 → 826 results).
- Date filter sent epoch *days*; Meta ignores them (ISO strings work; it means "ran during", not "launched in").
- Frontend-version discovery regex never matched the JS-escaped JSON.
- "recent" sort used a mode name Meta does not expose; now `relevancy_monthly_grouped` (newest launch month first).
- Continuation sessions were never stored when no challenge cookie was issued (`if (cookie)` on an empty string), and
  the in-memory map never evicted.
- Query expansion order put generic promo phrases first — harmless only because paging was broken. Seeds now run first;
  modifiers/discovery are opt-in. Historical data: only 14% of ads in the old registry (1,924 / 13,987) were found by a
  term the user typed; the rest came from promo/modifier phrases (app installs, marketplaces, gambling).
- Progress sat at 0% until a shard finished (now heartbeat + collected/target).
- Meta's `collation_count` (ads sharing a creative), page likes/categories, AI flag, link description etc. were discarded.

## Facts established (live)

- No pagination depth cap: full pools are reachable. Continuation pages are fixed at 10 ads regardless of `first`.
- The continuation sort mode must match the initial page's mode.
- Numeric impressions exist for ~0.002% of commercial ads (2 of 121k stored); Meta's impression *rank* is what is usable.
- EU reach / age / gender data is **not** in the search or server-rendered details payload (needs the details-modal
  request captured from a browser) — still open.

## Speed, scale and Meta's rate limit (learned the hard way, 2026-11-04 afternoon)

**What happened.** A ramp at 1.5 s spacing (164 requests) and 1.0 s (60) looked clean, so a 5,000-ad scan was run with the
pace allowed to creep from 2.5 s to 1.5 s. It sustained ~0.65 requests/s for ~16 min (~490 requests, 4,936 ads fetched) and
then stopped with "1 continuation cursor failed". The failure reason was swallowed, so it was first mistaken for a depth cap.
Re-running the same chain failed on page 1 with Meta's own message **`Rate limit exceeded`** (GraphQL error, HTTP 200). It is
a temporary throttle on this connection (no account is involved); recovery time is being measured (`recovery.log` in the audit
scratch dir). 2.5 s (0.4 req/s) remains the only proven daily rate; a 1.5 s floor is NOT safe for a sustained 500-request scan.

**What was built from that.**
- Rate limits are recognised (message text, or Meta codes 4/17/32/341/368/613/80004) as `RateLimitedError`: a 5 -> 15 -> 30 min
  cool-down, at least double the baseline pace, **no speed-up for 2 h**, bounded retries (`RATE_LIMIT_RETRIES`, default 2), and a
  clear failure afterwards. Each event is stored in `rate_limit_events` with the request counts of the preceding 10/60 minutes, so
  the real threshold can be learned from data (`GET /api/health` -> `pacing.last_rate_limits`).
- Rolling request budget `MAX_REQUESTS_PER_HOUR` (default 900) spreads back-to-back heavy scans. Hunter's daily run needs ~200.
- The speed-up floor is OFF (`FASTEST_REQUEST_DELAY_MS` unset = baseline). Re-enable only with evidence.
- A running scan that is waiting out a rate limit reports `paused_ms`; the UI says so instead of looking frozen.
- Chain failures now name Meta's actual message and the page where they happened (and the end-of-scan note no longer claims
  the window was "exhausted" when the chain broke).

**Other fixes from the same session.** Per-page fixed 1 s sleep removed (the limiter paces); hard 30 s per-request timeout
(a silent socket used to stall ~5 min and surface as bare `terminated`); body-read drops are retried; `/api/search` honours
`"exact phrases"`; page cap per shard 400 -> 1,100 and a yield-aware budget for targets > 1,000 (impression-order windowed scans
keep only ~25-50% of fetched ads); **Max 5,000** preset and live pace / ETA / queue / pause in the scan panel.

**Where the real speed-up is.** Not a faster clock. Per request the lever is yield: `Newest first` order for launch windows
(density ~100% and stops at the window edge, versus 25-50% in impression order), novelty-aware stopping, and not re-collecting
what the registry already holds.

# AdSignal audit — 2026-11-04

## Outcome

Scans had been collecting about **one page per query since ~2026-07-15**. Fixed, deployed to the Mac mini
(launchd `com.eladsaar.meta-ad-library-api`, 127.0.0.1:4100) and verified live.

| Measure | Before | After |
|---|---|---|
| "posture corrector" US, active — ads collected | ~30 | **1,224 unique** of 1,294 reported (128 pages, 321 s) |
| Same, GB | ~30 | 577 of 596 (58 pages, 148 s) |
| Exact phrase, 90-day launch window, target 1,000 | ~90 typical | 674 (pool exhausted; 87 out-of-window set aside), 204 s |
| 7-day launch window, `recent` order | n/a | 342 launched in the week, 192 s |
| Advertiser sweep (Avernio, one page) | 16 ads known | 150+ ads, 400 variants, 41 s |

## Root cause (Meta error 1357054)

Meta rejects the GraphQL pagination POST unless it carries `sec-fetch-site: same-origin`,
`sec-fetch-mode: cors`, `sec-fetch-dest: empty`. Ruled out by A/B test: cookies, referer shape,
`sec-ch-ua`, the frontend `v` revision, `first`, extra comet params. The client reported it as "empty payload"
because Meta signals it via a top-level numeric `error`, not a GraphQL `errors` array. The old watchdog fetched
page 1 only, so it stayed green. Timeline from the DB: avg unique ads per scan 213–664 (Jul 12–14) → ~90 from Jul 15.

## Other defects fixed

- Quoted phrases silently ran as unordered keyword searches (`keyword_exact_phrase` never used: 1,286 → 826 results).
- Date filter sent epoch *days*; Meta ignores them (ISO strings work; it means "ran during", not "launched in").
- Frontend-version discovery regex never matched the JS-escaped JSON.
- "recent" sort used a mode name Meta does not expose; now `relevancy_monthly_grouped` (newest launch month first).
- Continuation sessions were never stored when no challenge cookie was issued (`if (cookie)` on an empty string), and
  the in-memory map never evicted.
- Query expansion order put generic promo phrases first — harmless only because paging was broken. Seeds now run first;
  modifiers/discovery are opt-in. Historical data: only 14% of ads in the old registry (1,924 / 13,987) were found by a
  term the user typed; the rest came from promo/modifier phrases (app installs, marketplaces, gambling).
- Progress sat at 0% until a shard finished (now heartbeat + collected/target).
- Meta's `collation_count` (ads sharing a creative), page likes/categories, AI flag, link description etc. were discarded.

## Facts established (live)

- No pagination depth cap: full pools are reachable. Continuation pages are fixed at 10 ads regardless of `first`.
- The continuation sort mode must match the initial page's mode.
- Numeric impressions exist for ~0.002% of commercial ads (2 of 121k stored); Meta's impression *rank* is what is usable.
- EU reach / age / gender data is **not** in the search or server-rendered details payload (needs the details-modal
  request captured from a browser) — still open.

## Runbook

- Deploy: `git checkout <branch>`; `npm --prefix web run build`; `launchctl kickstart -k gui/$(id -u)/com.eladsaar.meta-ad-library-api`;
  first boot after a schema change takes ~10–30 s. Verify `curl :4100/api/health/deep`.
- Rollback: `git checkout 1b51be3` (last pre-audit commit) and restart. Schema changes are additive (old code runs).
  Pre-audit DB copy: `/Volumes/Mini Extra/Agent Work/default/adsignal-audit-20261104/ad-library-pre-audit.db`.
- Restore a backup: `gunzip -c /Volumes/KingstonData/Backups/AdSignal/ad-library-<stamp>.db.gz > ad-library.db` with the
  service stopped.
- If pagination fails again: `/api/health/deep` returns the real Meta error code; capture a real browser pagination
  request and diff headers/variables against `buildPostHeaders()` / `buildSearchVariables()`.

## Reliability under load (measured 2026-11-04, after the audit)

| Test | Result |
|---|---|
| API latency during a running scan (627 health polls + 17 rounds of 500-row result/registry queries) | p50 1 ms, p95 3 ms, max 81 ms; heaviest query 143 ms |
| Process memory, one 275-ad scan | 15 → 72 MB |
| 10 simultaneous scan requests | all 202 in 0.15 s; ran FIFO (arrival order = finish order); 10/10 complete, 0 errors |
| 5 duplicate re-asks (client reconnect) | 5/5 attached to the existing job, no duplicate scans |
| Service restart with 4 scans queued, first running | all 4 complete; the interrupted one was re-queued and went 24 → 78 ads |
| Worst-case Hunter query (`foot drop`, unquoted, 40k-ad pool, 90 d, target 1000) | 5.4 min, 779 ads, bounded by the 400-page cap |

Changes: FIFO persisted scan queue (max 25, `queue_position`, `429 queue_full`), identical-request re-attach
(`attached_to_existing`), one automatic re-queue of a scan interrupted by a restart, `queue:false` for the old strict 409.
Hunter's `ad-library.js` `api()` now retries dropped connections and 502/503/504 (1/3/8/20 s); never 4xx.

Capacity limits that remain: one scan at a time (Meta politeness; ~4 ads/s), DB on the internal SSD (12 GB free; each
distinct ad is stored ~8x — 2.5 GB for 218 MB of unique payload), no API key.
